
цикл из раздела «Цикл», обновляет статусы и не переходит дальше, пока текущий
шаг не зелёный.

## Цикл выполнения одного тикета

```
1. ПОДГОТОВКА
   - прочитать файл тикета docs/tasks/<backend|frontend>/T-XX-*.md
   - прочитать указанную спеку целиком
   - убедиться, что зависимости тикета ✅

2. ИМПЛЕМЕНТАЦИЯ
   - код строго по спеке; файлы — по ARCHITECTURE.md
   - без комментариев в коде
   - бек: ошибки через echo.NewHTTPError, тексты EN; фронт: типы snake_case

3. ЛОКАЛЬНАЯ ПРОВЕРКА (первый проход)
   - бек:  gofmt -w . && go build ./... && go vet ./... && go test ./...
   - фронт: npm run build && npm run lint
   - тесты для логики, где указаны в тикете (scoring, jwt)

4. КОММИТ + ПАЙПЛАЙН
   - git add -A && git commit -m "T-XX: ..." && git push
   - следить за workflow (GitHub API) до deploy: success
   - КРАСНЫЙ пайплайн = чинить немедленно, к следующему тикету не переходить

5. ПРОД-ВЕРИФИКАЦИЯ (второй проход) — каждую ручку руками:
   - позитивные кейсы из критериев приёмки тикета (curl, реальный JWT
     через POST /auth с подписанным initData)
   - негативные кейсы (401 без токена, 400 невалидное тело, 403 чужое)
   - сверить фактический JSON со схемой из /swagger/doc.json
   - фронт: страница открывается на проде, сценарий проходится вживую

6. СТАТУСЫ
   - файл тикета → ✅, README-индекс папки → ✅, docs/common/status.md → ✅
   - docs/backend/api.md, database.md или spec-ui.md — если «как есть» изменилось
   - отдельный коммит "T-XX done" ИЛИ включён в коммит шага 4

7. ПЕРЕХОД к следующему тикету
```

## Правила автономного режима

- Не задавать вопросов: все решения искать в спеках и docs/common/. Если
  реальная развилка не покрыта спекой — выбрать вариант из спеки, пометить
  решённое в отчёте и продолжать.
- Не ломать main: каждый пуш должен приходить зелёным. Сломал — фикс до
  anything else.
- Тикет заблокирован внешним фактором (нужен доступ, нет данных) → статус 🚧
  с комментарием «блокер: …» в трёх местах, идти к следующему независимому.
- Коммиты не форсить, main не ребейзить.

## Глобальный критерий завершения (T-20, прогнать ДВАЖДЫ)

1. Кандидат (юзер A): auth → role=candidate → сохраняет резюме
2. Рекрутер (юзер B): auth → создаёт компанию → вакансию (TTL 24)
3. Рекрутер видит A в ленте/списке со скорингом → invite
4. A видит приглашение с дедлайном → accept → матч с контактом рекрутера
5. Просроченное приглашение → статус overdue → ответ невозможен (409)
6. Каждая страница фронта на проде открывается и отрабатывает сценарий
7. Все статусы в docs/tasks и status.md ✅, workflows зелёные
